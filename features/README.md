# AI-BDD-DEMO — AI Agent 工作規範

**文件版本：** 1.2  
**文件狀態：** Approved

## 1. 專案說明

AI-BDD-DEMO 是一個使用 AI 輔助行為驅動開發（AI-BDD）的練習專案。

本專案是一個會員登入網站，採用以下技術：

- Python + FastAPI
- Jinja2 + HTML + CSS
- SQLite
- pytest + pytest-bdd
- GitHub Actions
- Raspberry Pi Ubuntu + systemd

所有開發必須以經過 Human Reviewer 核准的規格與 Gherkin 為依據。

## 2. 規格與共用文件

本專案的主要文件如下：

| 檔案 | 用途 |
|---|---|
| `specs/functional/functional-spec.md` | 功能範圍與功能需求 |
| `specs/business/business-rules.md` | 業務規則與判斷條件 |
| `specs/technical/technical-spec.md` | 技術架構、安全性與部署要求 |
| `docs/system-standard.md` | 測試與主程式共用的介面約定 |
| `features/*.feature` | Gherkin 驗收情境 |
| `features/feature-index.csv` | Feature ID 與狀態索引 |
| `features/README.md` | Feature 管理規則與清單 |
| `tests/README.md` | 測試執行方式、驗證限制及角色交接 |
| `tests/COVERAGE.md` | Feature／Scenario 與測試的對應 |

AI 在進行工作前，必須讀取與任務相關的文件。

文件引用路徑若與實際目錄不同，必須核對實際檔案，不得假設內容。

如果規格互相衝突、缺少必要條件或存在未確認的業務規則，必須詢問 Human Reviewer，不得自行決定；不受影響的工作可以繼續。

## 3. AI 角色與修改權限

| 角色 | 主要職責 | 預設可修改範圍 |
|---|---|---|
| Human Reviewer | 核准需求、業務規則、技術規格、Gherkin 及重要設計，審查 PR 並決定合併 | 依專案管理權限維護與核准文件及變更 |
| AI Analyst | 分析需求、詢問業務規則、整理規格、產生 Gherkin 草稿 | `specs/` 草稿、未核准的 `features/`、Feature 索引 |
| AI Test Engineer | 依據已核准 Gherkin 建立 pytest-bdd、fixtures、整合與回歸測試 | `tests/` |
| AI Developer | 依據已核准規格與介面約定實作應用程式 | `src/` |
| AI Failure Analyst | 分析測試失敗原因並提出修正建議 | 原則上唯讀 |
| AI DevOps | 維護品質關卡、CI/CD、建置與部署設定，執行檢查並提供報告 | `.github/`、`deploy/`、`pyproject.toml` |

角色權限是工作範圍約束，並非作業系統強制權限。超出範圍的修改必須經 Human Reviewer 授權。

執行測試不專屬某一角色。各角色可以在任務授權內執行相關檢查，但不得因此取得修改其他角色檔案的權限。

## 4. Agent 執行規則

1. 每次執行任務前，必須先確認目前被指派的角色。
2. 先讀取根目錄本文件 `agents.md`。
3. 再讀取對應角色的 `agents/*.md`。
4. 讀取相關的已核准規格與共用介面約定。
5. 確認允許修改的檔案範圍。
6. 只修改本次任務必要的檔案。
7. 完成後回報修改內容、實際檢查結果及限制。
8. 未明確指派角色時，應先詢問，不得直接修改檔案。
9. 已有指定分支或 PR 時，先核對並延續，不重複建立、不覆寫他人工作或強制推送。
10. 未獲授權不得直接推送主分支。
11. AI 不得代替 Human Reviewer 核准需求、核准部署或合併 PR。

AI 角色是工作分工，不代表 Codex 會自動啟動多個 Agent。執行時必須明確指定角色及其指示文件。

## 5. 標準 AI-BDD 工作流程

1. Human Reviewer 提出需求。
2. AI Analyst 分析需求並提出需要釐清的問題。
3. AI Analyst 建立或修改規格草稿。
4. Human Reviewer 審查規格，透過對應 PR 的人類合併留下核准紀錄。
5. AI Analyst 產生或更新 Gherkin 草稿，提交 PR。
6. Human Reviewer 審查 Gherkin，確認語法檢查結果後合併對應 PR，完成 G1 的人工核准部分。
7. 必要時先提出共用介面與重要設計，由 Human Reviewer 核准。
8. AI Test Engineer 依已核准 Gherkin 與介面約定建立自動化測試。
9. AI Developer 依規格、介面約定與測試實作功能。
10. GitHub Actions 驗證 G1 核准紀錄的有效性，並執行 G2～G6。
11. 測試失敗時，由 AI Failure Analyst 分析原因並建議負責角色修正。
12. Human Reviewer 審查實作、測試與 CI/CD PR，決定是否合併。
13. G1～G6 全部通過，且符合 G7 要求後，才允許部署。

Gherkin PR 合併前的自動語法檢查，不得等待「同一個 PR 已合併」才執行，以免形成循環依賴。

需求或 Gherkin 未變更時，後續程式與 CI 變更不要求重新核准相同內容。

## 6. 品質關卡

| Gate | 檢查內容 | 必須通過 |
|---|---|---|
| G1 | Gherkin 語法、索引一致性及有效的人類需求／Gherkin 核准紀錄 |
| G2 | pytest-bdd 驗收測試 | 是 |
| G3 | Regression Tests | 是 |
| G4 | Ruff / Mypy | 是 |
| G5 | Bandit / pip-audit | 是 |
| G6 | Build / Integration Tests | 是 |
| G7 | Deployment Approval | 依環境 |

G1 必須通過。其自動檢查與人工核准機制依下列規則辦理。

### 6.1 G1：自動檢查與人工核准

G1 包含兩個部分：

1. **自動檢查：** Gherkin 語法正確、Feature ID 唯一、檔案與索引一致。
2. **人工核准：** Human Reviewer 確認相關需求與 Gherkin 符合預期。

本專案以「Human Reviewer 審查並合併對應規格／Gherkin PR」作為人工核准紀錄，不要求額外使用 GitHub Environment，也不要求每次 Actions 執行都重新按核准。

核准紀錄必須能查證：

- 對應的 PR 連結。
- 實際執行合併的人類帳號。
- 被核准的檔案與版本，例如 commit SHA 或檔案內容雜湊。
- 核准適用的需求與 Feature 範圍。

只有納入對應規格／Gherkin 內容、由 Human Reviewer 審查後合併的 PR，才能作為該內容的核准證據。程式或 CI 設定 PR 的合併，不能自動取代其他 Gherkin 的核准紀錄。

AI 不得將下列情況視為已完成人工核准：

- AI 自行把文件或 CSV 改成 Approved。
- PR 已開啟但尚未由人類合併。
- 只有自動檢查成功，沒有相應的人類核准紀錄。
- 以不相關 PR 或其他版本的核准取代目前內容。

### 6.2 G1 核准的延續與變更

1. CI 應確認目前使用的規格與 Gherkin，仍對應有效的核准紀錄。
2. 只有程式、測試或 CI 設定變更，且規格與 Gherkin 內容未變時，可以沿用既有核准。
3. 需求、業務規則或 Gherkin 的受影響內容變更後，必須重新經 Human Reviewer 審查。
4. 只有格式、路徑或其他不影響驗收行為的變更，也必須留下可追溯的變更紀錄；不得由 AI 默默推定其核准範圍。
5. 核准紀錄缺漏、無法讀取或與目前內容不一致時，應標示為「核准尚未驗證」，不得宣稱 G1 PASS。
6. 不受影響的 G2～G6 可以獨立執行以提供診斷，但不得因此略過部署前的 G1 要求。

AI DevOps 應依本節政策實作核准紀錄驗證。若需要新增紀錄格式或儲存位置，應先提出具體方案，由 Human Reviewer 確認並授權相關檔案修改。

### 6.3 G2～G6 與 PR 審查

G2～G6 主要由工具自動執行，不要求每次由人類按下執行核准。

但自動檢查通過，不代表測試覆蓋、架構、風險與需求符合性已全部證實；Human Reviewer 仍負責審查 PR 並決定合併。

人類合併 PR，不會讓失敗、跳過或尚未執行的自動檢查變成 PASS。

正式品質關卡結果必須對應實際受測版本。其他 commit 曾通過檢查，不代表目前版本已通過。

### 6.4 G7：部署核准

G7 與 G1 是不同的核准目的：

- G1 確認需求與驗收標準。
- G7 確認是否允許部署已驗證版本。

本文件採用 PR 合併作為 G1 核准紀錄，不會取消 G7 的部署核准要求。

是否使用 production Environment 及其 Required reviewers，由部署政策決定。AI 不得代替人類完成部署核准。

## 7. 規格變更管理

1. AI 不得自行發明業務規則。
2. 已核准的業務規則不得未經授權修改。
3. 已核准的 Gherkin 不得未經授權修改。
4. 既有 Feature ID 不得任意重新編號。
5. 新 Feature ID 必須唯一。
6. `features/feature-index.csv` 由 AI Analyst 維護。
7. `features/README.md` 必須與 Feature 索引一致。
8. 修復 Bug 時，不得擅自改變已核准的業務行為。
9. 重構程式時，不得改變外部可觀察的業務行為。
10. 不得為了通過測試而刪除、停用或弱化測試。
11. 技術限制變更必須經 Human Reviewer 核准。
12. 核准紀錄須對應被審查的實際內容；後續變更不得繼續冒用舊版本核准。
13. 各角色文件及 workflow 若仍引用舊的 G1 Environment 核准方式，應在授權範圍內同步調整；修改文件本身不代表 workflow 已自動更新。

## 8. 測試失敗處理

當 G2～G6 失敗時：

1. AI Failure Analyst 分析失敗報告。
2. 判斷失敗原因與受影響範圍。
3. 建議由適當角色進行修正。
4. 修正角色只能修改授權範圍內的檔案。
5. 修正後重新執行相關測試及所有必要品質關卡。
6. 未經核准不得修改業務規則或 Gherkin 以取得 PASS。

環境安裝失敗、記憶體不足、收集失敗、零個測試、逾時、未執行及產品行為斷言失敗，必須分開說明，不得混稱為主程式錯誤或有效的 Red。

### 8.1 問題修正優先級

所有 AI 角色在審查規格、設計、程式、測試或 CI/CD 時，統一使用以下修正優先級。數字越小，處理優先順序越高。

| 優先級 | 定義 | 處理原則 |
|---|---|---|
| P0：緊急 | 已發生或有明確證據顯示即將造成重大事故，例如正式資料大量毀損、重大機密洩漏或核心服務全面中斷 | 立即回報 Human Reviewer，優先處理；涉及該問題的交付或部署應暫停 |
| P1：高 | 核心功能、重要安全控制或資料正確性有重大缺陷，例如登入驗證可被繞過、ETL 產生錯誤資料 | 優先修正，修正並驗證前，不建議合併或部署受影響內容 |
| P2：一般 | 特定情況下的功能錯誤、測試缺口或維護問題，具有具體影響，但未達 P0／P1 | 列明影響與修正建議；由 Human Reviewer 決定是否須在本次合併前完成 |
| P3：低 | 不影響既定行為、資料正確性或安全控制的輕微改善，例如命名、重複說明或可讀性問題 | 可安排後續改善 |

審查與回報規則：

1. 每項問題須提供優先級、問題描述、檔案與行號或文件章節、觸發條件、影響、證據及修正建議。
2. 優先級須根據實際影響、發生條件及證據判定，不得只因問題涉及「安全」或「測試」就固定分級。
3. 必須區分「已重現的缺陷」「靜態檢查發現的問題」與「尚待驗證的風險」；證據不足時，明確標示限制。
4. 測試無法偵測某種錯誤，不代表正式程式已發生該錯誤；應分別說明測試缺口與產品缺陷。
5. 修正優先級不等於品質關卡結果。P0～P3 用於安排問題處理順序，G1～G7 用於判定交付條件；不得以優先級較低為由將失敗的必要關卡視為通過。
6. 優先級不擴大 Agent 的修改權限；所有修正仍須遵守角色範圍及本次任務授權。
7. Human Reviewer 決定問題的處理順序及交付安排；AI 不得自行核准、合併或略過必要品質關卡。

## 9. 部署規則

1. 部署目標為 Raspberry Pi Ubuntu。
2. 目標機器預先安裝必要系統套件。
3. 使用 Python 虛擬環境及 systemd 執行網站。
4. 使用 GitHub Actions 透過 SSH 進行部署。
5. 部署前必須確認 G1～G6 全部通過，且對應同一待部署版本。
6. G7 人工核准依環境設定。
7. CD 不執行部署後自動化測試。
8. 部署不得覆蓋 SQLite 資料庫、Session、環境設定及機密。
9. 部署完成後，由 Human Reviewer 自行進行功能驗證。
10. 未明確授權部署的任務，不得因品質檢查成功就自行上傳或啟動部署。

## 10. 核心原則

**人類決定需求與驗收標準，AI 負責在核准的規格範圍內產生測試、實作程式與維護自動化流程。**

G1 的人類核准透過對應規格／Gherkin PR 的審查與合併留下紀錄，不要求每次 CI 重複核准。

當規格不明確時，先詢問，不得猜測。

當測試失敗時，先分析原因，不得透過修改驗收標準掩蓋問題。

自動檢查成功、人工審查完成及部署核准是不同事項，必須分別留下可追溯的證據。

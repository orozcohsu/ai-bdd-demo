# AI-BDD-DEMO 技術規格

**文件版本：** 1.2  
**文件狀態：** Approved  
**審核角色：** Human Reviewer

## 第一章：系統架構

### TECH-001：應用程式架構

1. 使用 Python 3.12 或相容版本開發。
2. 使用 FastAPI 作為 Web Framework。
3. 使用 Uvicorn 執行 Web Application。
4. 系統採用 Server-Side Rendering（SSR），由 Python 後端產生 HTML。
5. 使用 Jinja2 作為 HTML Template Engine。
6. 第一版不使用 React、Vue 等前端框架。
7. Runner 與部署主機的 Python 版本及處理器架構可能不同，必須分別記錄並核對相容性。

### TECH-002：資料儲存

1. 使用 MariaDB 儲存會員帳號、密碼雜湊、登入失敗次數、鎖定到期時間及伺服器端 Session。
2. 本次將既有 SQLite 資料儲存替換為 MariaDB，不以 SQLite 作為 MariaDB 不可用時的自動備援。
3. 資料庫替換不得改變已核准的登入、失敗次數累計、帳號鎖定、解除鎖定、錯誤訊息及 Welcome 存取行為。
4. 登入失敗次數及鎖定到期時間必須持久化儲存，不得只保存在應用程式記憶體。
5. 應用程式重新啟動，不得清空會員、失敗次數、鎖定狀態或尚未到期的 Session。
6. 資料庫資料、備份及連線機密不得納入 Git Repository。
7. 正式、開發與測試資料必須隔離，不得讓自動化測試連線正式資料庫。

### TECH-003：資料庫連線設定

1. 連線設定由外部環境提供，不在程式碼中硬編碼。
2. 至少須明確定義：
   - MariaDB 主機位置或 Unix Socket。
   - TCP Port；使用 Unix Socket 時依選定連線方式處理。
   - 資料庫名稱。
   - 連線帳號。
   - 連線密碼。
   - 連線逾時及必要的安全設定。
3. 本次指定的應用程式資料庫帳號為 `bdd`。
4. 資料庫帳號與網站會員帳號分開管理，不得混用。
5. 密碼透過受保護的外部設定提供，不寫入規格、程式、測試、Git 或日誌。
6. 必要設定缺少或無法連線時，必須明確回報，不得默默改用另一個資料庫。
7. 應用程式帳號依實際操作需求配置權限；資料庫建立、結構調整與一般執行權限應分開規劃。
8. 連線參數的共用介面及設定名稱，另於 `docs/system-standard.md` 定義。

### TECH-004：資料表與交易一致性

1. 使用支援交易及外鍵的儲存引擎，例如 InnoDB。
2. 資料表須能保存會員、密碼雜湊、失敗次數、鎖定期限及 Session 所需資料。
3. 資料型別與索引必須配合實際查詢、唯一性及持久化需求設計。
4. 同一會員的失敗次數讀取、累計、鎖定判定及更新，必須具有交易一致性。
5. 不得直接沿用 SQLite 的 `BEGIN IMMEDIATE` 作為 MariaDB 交易實作。
6. Developer 應提出適當的交易與鎖定方式，確保並行請求不會遺失失敗次數或錯誤解除鎖定。
7. 交易失敗時必須正確回滾，連線與游標須適當關閉或歸還。
8. SQL 必須使用參數化查詢，不以字串拼接使用者輸入。
9. 字元集及排序規則不得無意改變既有帳號比對行為，包括大小寫及空白處理。
10. 若資料表設計需要新增帳號長度、格式或其他業務限制，必須先提出影響，由 Human Reviewer 決定，不得自行加入。

### TECH-005：資料庫驅動與資料存取

1. 選用支援 MariaDB，且與 Runner、樹莓派 Python 及處理器架構相容的 Python 驅動。
2. 驅動選型及必要系統依賴須記錄於技術設計或交接文件，並由 `pyproject.toml` 管理 Python 相依套件。
3. 是否使用 ORM，由 Developer 根據既有結構提出必要性與取捨，不因更換資料庫而強制導入大型框架。
4. 資料庫連線、SQL 與交易邏輯應集中於資料存取責任範圍，不分散到網頁模板或路由。
5. MariaDB 連線型別、游標及例外，不應成為測試與業務服務不必要的跨模組依賴。

## 第二章：網頁介面設計

### UI-001：視覺風格

1. 網站以淡藍色作為主要視覺色調。
2. 登入頁與 Welcome 頁採用一致的設計風格。
3. 網頁須支援桌面與手機瀏覽器。
4. 使用 HTML、CSS 實作，不依賴大型前端框架。
5. 本次資料庫替換不改變既有網頁設計。

### UI-002：登入頁面

1. 提供帳號輸入欄位。
2. 提供密碼輸入欄位，密碼不得以明文顯示。
3. 提供登入按鈕。
4. 登入失敗時，於頁面顯示對應的錯誤訊息。

重設按鈕及鍵盤焦點行為，依已核准功能規格與業務規則辦理。

### UI-003：Welcome 頁面

1. 登入成功後顯示 Welcome 頁面。
2. 顯示歡迎訊息。
3. 未登入的使用者不得直接進入 Welcome 頁面。

## 第三章：登入與安全設計

### SEC-001：密碼安全

1. 密碼不得以明文儲存。
2. 使用安全的密碼雜湊演算法，例如 Argon2id。
3. 不得將密碼寫入 Log。
4. 不得在程式碼中硬編碼正式環境密碼或 Secret Key。
5. 如遷移既有會員資料，應保存原有有效密碼雜湊，不得將其轉回明文或再次當作明文密碼雜湊。

### SEC-002：Session 管理

1. 使用伺服器端 Session 管理登入狀態。
2. 瀏覽器只保存不含敏感資料的 Session ID。
3. Session Cookie 設定 HttpOnly、SameSite，HTTPS 環境啟用 Secure。
4. Session 必須具備有效期限。
5. 未登入使用者存取 Welcome 頁面時，導向登入頁。
6. Session 持久化改由 MariaDB 負責，不改變既有登入狀態及到期判定行為。
7. 應用程式重新啟動，不得因重新初始化而刪除仍有效的 Session。

本練習環境已確認使用：

- Session 有效期限：30 分鐘。
- SameSite：Lax。
- HTTP 練習環境：Secure Cookie 關閉。
- HTTPS 環境：Secure Cookie 開啟。

上述練習設定不自動成為其他正式環境的部署政策。

資料庫切換時是否保留舊 Session，屬於資料遷移決策，須依第九章確認，不預設已決定。

### SEC-003：帳號鎖定

1. 登入失敗次數及鎖定到期時間由伺服器端管理，持久化於 MariaDB。
2. 依據已核准的 `specs/business/business-rules.md` 實作。
3. 使用 UTC 表達及處理鎖定時間；資料庫欄位與應用程式之間的轉換須保持一致。
4. 不得依賴瀏覽器端計數來判定帳號鎖定。
5. 連續登入失敗次數與鎖定狀態的更新，須避免並行請求造成計數錯誤。
6. 資料庫替換不得改變第三次連續失敗鎖定、鎖定 60 秒、不延長原鎖定期限，以及到期重設等既有規則。
7. 不存在帳號的處理，仍依已核准業務規則辦理，不因資料庫替換而新增鎖定規則。

### SEC-004：Web 安全

1. 正式環境使用 HTTPS；目前經確認的 HTTP 練習環境例外另依 SEC-002 設定。
2. 登入表單須具備 CSRF 防護。
3. 所有輸入必須進行伺服器端驗證。
4. HTML 輸出須避免 XSS 風險。
5. 不得將機密資訊或詳細系統錯誤顯示給使用者。
6. MariaDB 連線錯誤、SQL、連線字串及資料庫密碼，不得直接顯示於網頁或未經處理的日誌。

## 第四章：程式碼結構

### CODE-001：模組責任

正式應用程式放在 `src/`，各模組適當分離職責：

1. `main.py`：建立 FastAPI Application、註冊路由及接合服務。
2. `auth.py`：實作登入驗證、登入失敗計數及帳號鎖定。
3. `db.py` 或對應資料存取模組：管理 MariaDB 連線、資料存取及交易。
4. `config.py` 或對應設定模組：載入並驗證外部設定。
5. `templates/`：存放登入頁與 Welcome 頁的 HTML。
6. `static/`：存放 CSS 等靜態資源。
7. 資料庫存取邏輯應與網頁路由分離，避免所有程式碼集中於 main.py。

應用入口及共用介面遵循已核准的 `docs/system-standard.md`。

本次資料庫設定及測試接合方式變更，須先同步修訂共用介面約定，再交付 Test Engineer 與 Developer 使用。

### CODE-002：程式品質

1. 使用 Python Type Hints。
2. 使用 Ruff 執行 Lint。
3. 使用 Mypy 執行 Type Check。
4. 使用 pytest、pytest-bdd 執行自動化測試。
5. 一般函數、類別與組合方式，由 AI Developer 依需求及既有架構合理選擇。
6. 不為套用 Design Pattern 而增加不必要的複雜度。
7. 影響重要架構或既有共用介面的設計變更，須先提出方案並取得核准。
8. 不得以修改已核准的業務預期，掩蓋資料庫替換造成的缺陷。

## 第五章：測試與品質關卡

### QA-001：品質檢查

所有程式變更必須符合以下自動品質要求：

| Gate | 自動檢查內容 |
|---|---|
| G1 | Gherkin 語法、Feature ID、索引及既有需求／Scenario 追溯一致性 |
| G2 | pytest-bdd 驗收測試 |
| G3 | Regression Tests |
| G4 | Ruff／Mypy |
| G5 | Bandit／pip-audit |
| G6 | Build／Integration Tests |

人類需求核准由既有需求討論、規格及 Gherkin 審查流程處理，不在 CI 額外建立人工核准等待點。

CI 不得：

1. 要求本次 PR 先合併，才能通過本次 PR 的自動檢查。
2. 只因缺少特定格式的歷史核准 PR、合併帳號或核准表，就讓自動檢查失敗。
3. 建立 `requirements-review` Environment 作為每次品質檢查的必要等待點。
4. 將自動檢查 PASS 宣稱為 AI 已代替人類核准需求。

規格或 Gherkin 的受影響內容變更後，仍須提交 Human Reviewer 審查；未變更內容不要求重複核准。

AI DevOps 應在對話提供 G1～G6 結果表格、實際證據及問題，由 Human Reviewer 決定後續調整及 PR 是否合併。

人類合併 PR，不會讓失敗、跳過或未執行的檢查變成 PASS。

### QA-002：測試要求

1. 測試不得依賴正式環境資料庫。
2. 與資料存取相關的驗收及整合測試，必須使用隔離的真實 MariaDB，不以 SQLite 代替。
3. 每個測試案例的資料必須隔離；案例內需要重啟應用時，保留同一案例的資料庫內容。
4. 測試資料建立與清理不得影響其他案例或正式資料。
5. 測試須驗證會員、失敗次數、鎖定期限及 Session 在應用重啟後的持久化行為。
6. 並行失敗計數及鎖定一致性，必須在 MariaDB 上實際驗證。
7. 帳號鎖定時間測試應使用可控制的時鐘，不以實際等待 60 秒進行。
8. 已核准的 Gherkin 不得由 AI Developer 為了讓測試通過而自行修改。
9. 測試程式放在 `tests/`，依已核准情境與共用介面約定執行。
10. 鍵盤焦點及訊息可見性等瀏覽器行為，使用真實瀏覽器驗證。
11. SSR 檢查應直接驗證原始 HTTP HTML，不以瀏覽器渲染後 DOM 取代。
12. 零個測試、收集失敗、環境錯誤、逾時與未執行，不得視為 PASS。
13. 主程式未實作或資料庫環境缺少造成的錯誤，不得宣稱為有效的行為 Red。
14. 既有測試中依賴 SQLite 檔案存在的斷言，應改為驗證真正的資料隔離與持久化行為，不得直接刪除其驗證目的。
15. 只驗證純函數或測試輔助工具、沒有資料庫互動的測試，不必為湊數強制連線 MariaDB。

### QA-003：Runner 與建置驗證

1. 正式自動檢查在 GitHub Runner 的隔離環境執行。
2. Runner 安裝所需 Python、正式依賴、測試工具及匹配的瀏覽器。
3. Runner 啟動獨立 MariaDB 測試服務，版本須與選定部署版本對齊或有明確相容性依據。
4. 等待資料庫服務可用後，才執行依賴資料庫的測試。
5. Runner 使用獨立測試帳號及憑證，不使用正式資料庫連線資訊。
6. 記錄實際受測 commit、OS、Python、MariaDB、驅動及主要相依版本。
7. 本地驗證可作為開發證據，但不取代正式 Runner 結果。
8. 建置產物須包含必要模板與靜態資源。
9. 在隔離環境安裝 wheel，從 Repo 外連線隔離 MariaDB，驗證真實應用、頁面與必要資源。
10. 建置或 import 成功，不代表完整的安裝與整合驗證通過。
11. Runner 環境與 Raspberry Pi 實機不同，應如實記錄尚未驗證的架構與版本相容性限制。

## 第六章：部署環境與資料遷移

### DEPLOY-001：目標環境

1. 部署目標為 Raspberry Pi Linux；實際 OS、處理器架構及 Python 版本須記錄於部署交接。
2. 目前已部署的主機環境為 32 位元 ARM、Python 3.13.5；後續以部署前實際核對結果為準。
3. 目標機器的 MariaDB、Python Runtime、系統及 Python 套件，由 Human Reviewer 手動安裝及維護；另有明確授權時，AI 才能協助。
4. 依 Human Reviewer 已確認的執行方式，直接使用主機 Python，不強制建立或使用 Python Virtual Environment。
5. 使用 systemd 管理 FastAPI 服務。
6. 目前練習網站使用 Port 8000；服務埠與資料庫連線埠分開設定。
7. MariaDB 資料由資料庫服務管理，與應用程式上傳目錄分開保護。
8. 部署程式不得覆蓋或刪除資料庫資料。
9. Session、環境設定及機密，須與可覆寫的應用程式檔案分開保護。

### DEPLOY-002：持續部署

1. GitHub Actions 執行 G1～G6 自動品質檢查。
2. 全部必要自動檢查通過，且符合部署授權及適用 G7 要求後，才允許進入 CD。
3. CD 使用 SSH 傳輸已通過檢查版本的指定必要檔案。
4. 必須確認上傳內容與受測版本一致，不以當下最新 main 取代已驗證版本。
5. 品質檢查與部署流程分開；PR 品質工作不得取得部署憑證或觸發正式上傳。
6. CD 不刪除遠端既有檔案，不覆蓋 Secret、Session、環境設定、資料庫資料或備份。
7. CD 不執行部署後自動化測試；正式環境功能由 Human Reviewer 手動驗證。
8. G7 依環境政策設定；正式環境預設須經人工部署核准。
9. G1 不另設 CI 人工等待點，不代表取消 G7 的部署授權。
10. 未明確授權部署的工作，即使品質檢查通過，也不得自行上傳或啟動正式服務。

### DEPLOY-003：遠端操作限制

本專案預設 CD 僅上傳經授權的必要專案檔案。

除非另有明確授權，不得在遠端：

- 安裝、更新或移除系統與 Python 套件。
- 建立虛擬環境。
- 建立或修改正式資料庫結構。
- 執行資料搬移或資料庫遷移。
- 啟動或重啟服務。
- 執行測試。
- 切換正式服務指向的版本路徑。

必要服務操作與功能驗證，由 Human Reviewer 執行，或另行明確授權 AI 協助。

上傳成功只表示檔案傳輸完成，不表示網站已更新或功能正常。

### DEPLOY-004：SQLite 至 MariaDB 資料遷移

1. 程式改用 MariaDB，不代表既有 SQLite 資料已完成遷移。
2. 遷移前須確認資料保留範圍，包括：
   - 會員帳號與密碼雜湊。
   - 登入失敗次數。
   - 鎖定到期時間。
   - 既有 Session。
3. 是否保留上述資料及切換時的處理方式，由 Human Reviewer 決定，不自行清空或重新建立會員。
4. 執行遷移前，必須備份來源 SQLite；目標 MariaDB 若已有資料，也須先評估並保護既有內容。
5. 不得因帳號重複而自動覆寫既有會員或密碼。
6. 遷移須核對資料筆數、必要欄位、密碼雜湊、時間表示及資料關聯。
7. 正式切換期間如何避免新資料繼續寫入舊 SQLite，須在遷移方案中明確說明。
8. 切換方案須包含失敗處理及回復方式；回復時不得忽略切換後的新資料。
9. 未取得明確遷移授權前，不得執行正式資料搬移。
10. 資料保留及 Session 決策尚未確認時，只能先進行不依賴該決策的規格、設計與隔離測試工作。

## 第九章：MariaDB 設定與資料遷移決策

### 9.1 已確認的連線設定

| 項目 | 設定 |
|---|---|
| MariaDB Server 版本 | 11.8.6-MariaDB |
| 部署位置 | 與網站相同的樹莓派主機 |
| 連線方式 | TCP |
| 連線主機 | `127.0.0.1` |
| TCP Port | `3306` |
| 資料庫名稱 | `bdd` |
| 應用程式連線帳號 | `bdd` |
| 連線密碼 | 由受保護的外部設定提供，不寫入 Git、規格或日誌 |
| 應用程式執行方式 | 直接使用樹莓派主機 Python，不使用虛擬環境 |

資料庫帳號必須允許上述 TCP 連線方式；實作及部署時核對實際權限，不假設帳號建立後即可從所有來源連線。

### 9.2 資料遷移範圍

1. 既有 SQLite 的全部應用資料表與資料，均須遷移至 MariaDB。
2. 遷移範圍包含但不限於：
   - 會員帳號。
   - 原有密碼雜湊。
   - 連續登入失敗次數。
   - 鎖定到期時間。
   - Session 記錄及到期時間。
3. 不重新設定既有會員密碼，不將既有雜湊再次當作明文密碼雜湊。
4. 不清空失敗次數、不提前解除鎖定，也不任意使有效 Session 失效。
5. 遷移 Session 時，須核對既有應用機密設定與 Cookie 行為，保留維持登入狀態所需的設定。
6. MariaDB 資料表結構可依相容性調整，但須保留資料意義、唯一性、關聯及既有業務行為。
7. 若目標資料庫已有同名資料表或資料，先回報衝突，不直接刪除或覆寫。

### 9.3 未指定技術細節的處理原則

1. 一般技術細節由 Developer 與 DevOps 依本規格、既有架構及相容性合理決定，記錄主要選擇，不要求 Human Reviewer 逐項決定函式、參數或工具細節。
2. 資料表使用 InnoDB，文字資料使用 UTF-8 相容字元集。
3. 帳號欄位的排序與比較設定，必須維持既有大小寫及空白比對行為，不直接套用會改變登入結果的資料庫預設值。
4. 日期及時間維持 UTC 語意，保留鎖定與 Session 到期判斷所需精度。
5. Python 驅動須能在現有樹莓派架構及 Python 版本運作，版本於實作時固定並驗證。
6. Runner 使用隔離的 MariaDB 11.8.6 測試服務及獨立測試憑證，不連線樹莓派資料庫。
7. 「使用預設」不代表允許降低安全控制、改變業務規則、覆寫資料或略過測試。

### 9.4 預設切換方案

1. 採短暫維護期間切換，遷移時停止應用程式寫入 SQLite。
2. 先備份 SQLite，保留原始資料，不刪除來源檔案。
3. 建立 MariaDB 結構並搬移全部應用資料。
4. 核對資料表、筆數、欄位值、密碼雜湊、時間及資料關聯。
5. 驗證完成後，修改外部連線設定，使應用程式改用 MariaDB，再啟動服務。
6. 切換前失敗時，不啟用不完整的 MariaDB 資料。
7. 切換後若已有新資料寫入 MariaDB，不得直接退回舊 SQLite 而遺失新資料；須先停止寫入並評估資料一致性。
8. 實際備份、建表、搬移、停止及重新啟動服務，仍須在明確授權的部署／遷移任務中執行；本規格審核不代表已執行上述操作。

## 2. 應用入口與設定

### 2.1 應用入口

保留既有入口：

`ai_bdd_demo.main:create_app`

```python
create_app(*, settings: AppSettings, clock: Clock | None = None) -> FastAPI
```

操作環境保留：

`ai_bdd_demo.main:create_app_from_environment`

此入口從外部環境載入設定，再呼叫相同的 `create_app`，不得另外實作一套登入流程。

測試可使用符合相同屬性約定的設定物件，不必強制依賴某個具體設定類別。

### 2.2 MariaDB 設定欄位

本次移除應用執行設定中的 `database_path`，改用以下連線欄位：

| 設定欄位 | 約定 |
|---|---|
| `settings.db_host` | MariaDB 主機；目前部署為 `127.0.0.1` |
| `settings.db_port` | TCP Port；目前部署為 `3306` |
| `settings.db_name` | 資料庫名稱；目前部署為 `bdd` |
| `settings.db_user` | 應用程式連線帳號；目前部署為 `bdd` |
| `settings.db_password` | 外部提供的資料庫密碼，不寫入 Git、日誌或物件的可讀輸出 |
| `settings.db_connect_timeout_seconds` | 正整數，預設 10 秒，可由外部調整 |
| `settings.secret_key` | 外部提供的應用機密，不寫入 Git 或日誌 |
| `settings.cookie_secure` | HTTPS 為 true；目前 HTTP 練習環境明確設為 false |
| `settings.session_ttl_seconds` | 正整數；目前練習環境為 1800 秒 |
| `settings.cookie_samesite` | 目前練習環境為 `lax` |
| `clock` | 提供 UTC 時間；未傳入時使用真正系統時鐘 |

設定的可讀輸出、例外及日誌不得包含資料庫密碼或 Secret Key。

`database_path` 不再是 MariaDB 執行或測試介面；舊 SQLite 路徑只屬於獨立遷移工作的來源設定。

### 2.3 外部環境變數

| 環境變數 | 對應設定 |

| `AI_BDD_DB_HOST` | `db_host` |
| `AI_BDD_DB_PORT` | `db_port` |
| `AI_BDD_DB_NAME` | `db_name` |
| `AI_BDD_DB_USER` | `db_user` |
| `AI_BDD_DB_PASSWORD` | `db_password` |
| `AI_BDD_DB_CONNECT_TIMEOUT_SECONDS` | `db_connect_timeout_seconds` |
| `AI_BDD_SECRET_KEY` | `secret_key` |

| `AI_BDD_SESSION_TTL_SECONDS` | `session_ttl_seconds` |
| `AI_BDD_COOKIE_SAMESITE` | `cookie_samesite` |

規則：

1. 除已定義的連線逾時預設值外，操作環境明確提供必要設定，不在程式中放入正式憑證。
2. 不自動讀取正式連線資訊供測試使用。
3. 缺少必要設定時，應用啟動失敗並回報不含機密的原因。
4. 不能連線 MariaDB 時，不自動退回 SQLite。
5. 不輸出包含密碼的完整連線字串。

## 3. 應用生命週期與資料庫結構準備

### 3.1 一般應用啟動

1. 匯入模組或建立設定物件時，不建立資料庫、資料表或預設會員。
2. 應用啟動生命週期建立必要服務及連線管理資源，確認指定資料庫可用。
3. 正常啟動不得清空資料、重建資料庫或覆寫會員。
4. 正常啟動不得自動將 SQLite 搬移至 MariaDB。
5. 結束生命週期時，釋放連線及其他資源，不刪除資料。
6. 必要資料表尚未準備完成時，回報明確錯誤，不假裝應用已正常可用。

### 3.2 資料表初始化接合

提供正常的資料庫結構準備介面：

```python
ai_bdd_demo.db.initialize_schema(*, settings: AppSettings) -> None
```

約定：

1. 連線至已存在、由設定明確指定的資料庫。
2. 建立本版本必要的資料表與索引。
3. 不建立預設會員。
4. 不刪除、清空或覆寫既有資料。
5. 不將此介面作為任意版本結構變更的通用遷移工具。
6. 既有結構不相容時，回報問題，不自行破壞性修改。
7. 此介面是一般部署準備工具，不是公開 HTTP API 或測試後門。

正式環境的資料庫建立、結構準備及資料遷移，依明確授權的操作流程執行。

測試環境可以在建立隔離資料庫後呼叫相同介面，不另外建立假資料存取系統。

建立資料庫及準備結構所需權限，與應用程式正常執行權限分開管理，不為方便測試而擴大正式帳號權限。

## 4. HTTP 路由及表單

本次資料庫替換保留既有路由與狀態碼。

| 方法／路徑 | 回應約定 |
|---|---|
| `GET /` | 303，Location 指向 `/login` |
| `GET /login` | 200，回傳含完整登入表單的 HTML |
| `POST /login` 成功 | 303，Location 指向 `/welcome`，建立真正的伺服器端登入狀態 |
| `POST /login` 業務驗證失敗或鎖定 | 200，重新呈現登入頁及業務規格指定的錯誤訊息；不得因此新建登入狀態 |
| `POST /login` 缺少／無效 CSRF 證明 | 403，不完成登入；不額外約定失敗計數變化 |
| `GET /welcome` 有效登入 | 200，HTML 含歡迎訊息 |
| `GET /welcome` 未登入 | 303，Location 指向 `/login` |

表單以 POST 提交至 `/login`：

| 元素 | 穩定介面 |
|---|---|
| 帳號欄 | `name="username"`、`id="username"`，有對應 label |
| 密碼欄 | `name="password"`、`id="password"`、`type="password"`，有對應 label |
| CSRF 欄 | 隱藏欄位 `name="csrf_token"`，由伺服器產生與驗證 |
| 登入按鈕 | 可及名稱「登入」、`type="submit"` |
| 重設按鈕 | 可及名稱「重設」，不提交登入請求 |
| 錯誤訊息 | `role="alert"` |
| Welcome 訊息 | `data-testid="welcome-message"`；不新增未核准的歡迎文案 |

正常登入測試先 GET 表單取得真正的 CSRF 證明，再 POST；不得停用安全機制。

CSRF 前置狀態不能被誤判為已登入 Session。

既有 Cookie 名稱及用途維持：

- `session_id`：登入 Session 的瀏覽器識別值。
- `csrf_proof`：CSRF 防護所需證明。

資料庫替換不得無必要地變更這些名稱及既有 Cookie 行為。

## 5. MariaDB 與內部資料介面

透過 `app.state.services` 取得正常內部服務物件。

這些介面不是 HTTP API；不得建立測試專用公開路由、繞過驗證參數或正式測試後門。

| 介面 | 行為 |
|---|---|
| `members.create(username, password_hash)` | 建立會員資料；不新增產品註冊功能。交易提交後，可供其他連線讀取 |
| `members.get(username)` | 回傳會員資料，包括內部驗證所需的 `password_hash`；不存在時回傳 None |
| `auth.get_account_state(username)` | 回傳既有會員目前有效的 `failed_attempts`、`locked_until`、`is_locked`；不存在時回傳 None |
| `sessions.get(session_id)` | 回傳有效 Session 的 `username`、`expires_at`；不存在或過期時回傳 None |

約定：

1. 保留上述介面名稱及既有行為，避免 Test Engineer 與 Developer 各自建立不同接合方式。
2. 回傳資料可使用具名唯讀物件。
3. `locked_until` 有值時，為帶 UTC 時區的 datetime；沒有鎖定期限時為 None。
4. `expires_at` 為帶 UTC 時區的 datetime。
5. 不向 HTTP 回應洩漏密碼雜湊或資料庫內部欄位。
6. 業務測試不固定資料庫游標型別或 SQL 實作。
7. 不使用 getter 的回傳值作為唯一驗收依據，仍驗證實際 HTTP 行為與持久化結果。
8. SQL、資料列轉換及連線管理集中於適當模組，不要求業務服務直接依賴特定驅動的型別。

### 5.1 交易與並行一致性

1. 同一會員的狀態讀取、到期處理、失敗累計及鎖定更新，須有適當交易保護。
2. 不直接沿用 SQLite 的 `BEGIN IMMEDIATE`。
3. Developer 依 MariaDB 技術規格選擇適當交易與鎖定方式，確保並行請求不遺失失敗次數。
4. 交易提交後的結果須能由另一個連線觀察。
5. 交易失敗須回滾，不留下一半完成的狀態。
6. 不以快取或應用記憶體取代必須持久化的鎖定狀態。
7. 不得因資料庫排序規則，無意改變帳號大小寫或空白比對行為。

### 5.2 測試前置資料

1. 使用真實密碼雜湊機制及正常內部資料介面建立測試會員。
2. 不使用正式會員或正式資料庫憑證。
3. 需要失敗兩次或已鎖定狀態時，透過真正的登入請求建立。
4. 不提供直接指定登入成功或鎖定結果的假介面。
5. 遷移工具直接搬移既有資料，與一般驗收測試建立前置狀態屬於不同工作，不混為測試後門。

## 6. 時鐘、到期與重新啟動

`Clock.now()` 回傳帶 UTC 時區的 datetime。

帳號鎖定與 Session 到期判定使用此來源，不另外使用無法由測試控制的系統時間或資料庫時間函式取代。

測試時鐘只提供時間，不計算登入結果。

約定：

1. T 為第三次連續失敗的時刻。
2. 測試直接調整到 T＋59、60、61 秒，不實際等待。
3. 鎖定期滿後，狀態查詢與下一次登入反映已解除鎖定、失敗次數重設。
4. 不強制使用背景排程更新到期狀態。
5. Session 到期同樣由可控制時鐘驗證。
6. 資料庫與應用程式間的時間轉換不得造成到期邊界偏移。

### 6.1 重新啟動測試

1. 關閉原應用生命週期。
2. 保留同一案例的 MariaDB 資料庫與資料。
3. 使用相同資料庫設定及可控制時鐘建立新應用。
4. 驗證失敗次數、原鎖定期限及登入結果。
5. 驗證尚未到期的 Session 仍依既有約定有效。
6. 不以刪除、清空或重新建立資料掩蓋持久化缺陷。
7. 不再使用 SQLite 檔案存在作為持久化證據。

## 7. 測試資料庫隔離

### 7.1 測試環境

1. 使用真實 MariaDB 11.8.6，不以 SQLite 或假資料庫替代資料存取驗收。
2. Runner 啟動獨立測試服務，不連線樹莓派上的 `bdd` 資料庫。
3. 測試連線資訊由測試專用環境設定提供，不從正式設定自動繼承。
4. 每個案例使用獨立資料庫；同一案例需要多個應用或重啟時，依測試目的共用或分開建立資料庫。
5. 測試資料庫使用可辨識、唯一的名稱，例如 `bdd_test_<run>_<case>`，符合 MariaDB 命名限制。
6. 缺少測試連線資訊時，明確失敗，不回退至正式資料庫。

### 7.2 Fixtures 責任

測試 fixtures 負責：

1. 等待隔離 MariaDB 服務可用。
2. 建立本次案例專用資料庫。
3. 使用正常結構初始化介面準備資料表。
4. 明確提供測試用資料庫設定、臨時 Secret Key 及可控制時鐘。
5. 啟動真實應用生命週期。
6. 案例結束後關閉 Client、伺服器及應用資源。
7. 僅清理該案例明確建立的測試資料庫。

清理必須核對目標為測試服務及本案例建立的資料庫，不得依模糊名稱批次刪除，不得清理正式 `bdd`。

測試所需的資料庫建立權限由測試環境配置，不因此擴大正式應用程式帳號權限。

### 7.3 獨立應用隔離

既有「兩個獨立 SQLite 檔案」測試，改為：

1. 建立兩個獨立 MariaDB 測試資料庫。
2. 各自建立真實應用實例。
3. 在其中一個資料庫建立會員並登入。
4. 驗證另一個資料庫沒有該會員或登入狀態。
5. 不只比較連線設定不同，必須核對實際資料與 HTTP 行為。

## 8. 瀏覽器與 HTTP 測試的界線

真實瀏覽器測試使用既有 label、role、id 辨識元素，不綁定 CSS 排版。

重設驗收必須由應用本身實現：

1. 填入資料，按下「重設」。
2. 核對兩欄皆空，`document.activeElement` 為帳號欄。
3. 不重新點選欄位，直接用鍵盤輸入。
4. 核對文字進入帳號欄且密碼仍空白。

測試不得自行清欄位或呼叫 focus 代替產品功能。

HTTP TestClient 不能證實鍵盤焦點或瀏覽器互動。

SSR 情境直接檢查 HTTP 原始 HTML 的欄位、按鈕及歡迎訊息，不只檢查 JavaScript 執行後的 DOM。

UI 重設可使用必要的少量瀏覽器腳本，不改變後端 SSR 架構。

瀏覽器測試：

1. 由 fixture 啟動真實應用。
2. 使用 loopback、臨時 HTTP Port 及同一案例的隔離 MariaDB。
3. 可控制時鐘由同一程序中的測試與伺服器執行緒共享。
4. 測試時鐘須具備執行緒安全性。
5. 不新增公開網路調時端點。

## 9. 安全、例外與並行接合

| 驗證 | 接合方式 |
|---|---|
| 密碼儲存 | 從正常內部介面讀取雜湊，使用真實演算法驗證測試密碼；不能只檢查與明文不同 |
| 日誌 | 擷取實際處理日誌，確認沒有輸入密碼、資料庫密碼或 Secret |
| Session | 同時核對 Cookie、對應伺服器紀錄及 Welcome 存取，不因 Cookie 存在就推定成功 |
| Cookie | 驗證 HttpOnly／SameSite，HTTPS 情境有 Secure；屬性驗證與真實 HTTPS 傳輸安全分開 |
| CSRF | 無效證明走正常路由，不替換安全驗證器；後續存取 Welcome 仍應未登入 |
| 受控內部錯誤 | 暫時替換測試實例正常資料介面的方法，使其拋出含測試標記的例外；驗證真實路由不洩漏細節 |
| 並行失敗計數 | 使用同一應用及 MariaDB，不同 Client 與獨立有效 CSRF 狀態同步送出請求，完成後核對真實狀態及後續登入行為 |
| 資料隔離 | 在不同測試資料庫建立應用，驗證會員、計數及 Session 不互相洩漏 |
| 重啟持久化 | 關閉並重建應用，保留原資料庫後驗證原有狀態 |

受控例外只用於錯誤處理情境，不能將登入或鎖定核心替換成固定結果。

方法替換由測試工具暫時執行，測試結束後還原，不新增正式應用故障開關。

HTTP 測試須取得應用回應，不讓測試工具直接重新拋出伺服器例外而略過回應驗證。

## 10. SQLite 至 MariaDB 遷移接合

本章定義後續遷移工作的資料相容性要求，不代表已授權或執行正式遷移。

### 10.1 遷移範圍

1. 來源 SQLite 的全部應用資料表及資料均須納入盤點與遷移。
2. 目前包含會員與 Session；不能只搬會員帳號。
3. 保留原有密碼雜湊、失敗次數、鎖定到期時間及 Session 資料。
4. 不將密碼雜湊重新當作明文密碼處理。
5. 不重新計算鎖定期限或延長 Session。
6. 不以「過期」或「目前未使用」為由，在本次全量搬移中自行省略資料。

### 10.2 Session 相容性

1. 保留既有 Session 識別值與伺服器端儲存表示之間的對應方式。
2. 目前伺服器端保存 Session token 的 SHA-256 指紋；搬移後須保持可由原 Cookie 查得同一筆資料。
3. 不在遷移過程改變 Cookie 名稱、Secret Key 或其他維持既有流程所需設定。
4. 有效 Session 切換後仍依原到期時間判定，不要求使用者因技術替換重新登入。
5. 已過期的 Session 即使保留資料，仍不得被視為有效登入。

### 10.3 結構與驗證

1. 一般 BDD 測試不固定資料庫表格布局；但遷移工具必須明確列出來源與目標的欄位、型別及關聯對應。
2. 不把 SQLite 專用系統表當作應用資料表搬移。
3. 核對應用資料表清單、筆數、必要欄位值、唯一性與關聯。
4. 核對 UTC 時間轉換及精度，避免鎖定或 Session 到期邊界改變。
5. 遷移至已有資料的目標時，不自動覆寫同名會員或資料，先回報衝突。
6. 來源備份、維護期間寫入控制、切換及回復依技術規格執行。
7. 正式遷移不得混入自動化測試資料。
